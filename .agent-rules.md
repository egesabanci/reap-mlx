# REAP MLX Agent Rules

These rules apply to implementation workers spawned through Agent Orchestrator.

## Role

- Codex workers implement code, tests, and narrowly scoped docs for assigned GitHub issues using `gpt-5.5`.
- DeepSeek/OpenCode orchestration handles planning, decomposition, review, and coordination.
- Do not broaden an issue without explicit coordination through the orchestrator.

## Core Objectives

- Preserve the existing PyTorch/CUDA REAP implementation as the production and official experimentation path.
- Build the MLX backend as a parallel Apple Silicon experimentation backend.
- Make MLX REAP work within MLX constraints without pretending it has CUDA/PyTorch semantics.
- Make MLX REAP adapter-driven so compatible MoE weights can be represented without hard-coding one architecture.
- Treat Qwen3 as the bootstrap/reference adapter only.

## Implementation Discipline

- Read the active issue, `implementation-plan-draft.md`, and relevant files before editing.
- Keep changes scoped to the issue and do not refactor unrelated CUDA/PyTorch code.
- Do not revert user changes or unrelated worktree changes.
- Prefer existing project patterns and small, testable modules.
- Put architecture-specific tensor names, router details, and expert layout behavior behind explicit adapter contracts.
- Use structured model metadata and tensor APIs over ad hoc string parsing where practical.
- Keep CLI, docs, and tests honest about MLX limitations and Apple Silicon experimentation scope.

## Verification

- Add or update focused tests for adapter contracts, model loading, routing traces, pruning, merging, and numerical invariants as appropriate for the issue.
- Run the narrowest meaningful verification first, then broaden when shared behavior changes.
- Report every verification command and whether it passed, failed, or was skipped.
- If GPU/CUDA-only or Apple Silicon-only validation cannot run in the worker environment, document the reason and provide the command that should be run manually.

## Git And PR Hygiene

- Work from the AO-created worktree and branch for the assigned issue.
- Do not use destructive git commands such as `git reset --hard` or `git checkout --` unless explicitly instructed by the user.
- Keep PRs issue-scoped and include the issue number in the PR description.
- Summarize changed files, behavior changes, tests, and residual risks before handing work back.
